# طرح آزمون سیستمی حاصل ۳۶۰ (نسخه مبنا: ۰.۷.۶)

## هدف
کاهش ورود دستی مکرر اطلاعات و تشخیص سریع خطای مالی، تقویمی، داده‌ای و ظاهری **بدون دست‌زدن به اطلاعات واقعی کاربر**.

## پیشنهاد ابزار و جایگاه آن
1. **Node.js test runner**: اجرای آزمون‌های هسته محاسبات نقدی، تسویه، انحراف بودجه، تقویم، مهاجرت و اعتبارسنجی، روی هر commit. مبنای جاری ۷۶ آزمون پاس‌شده است.
2. **Playwright**: آزمون صفحه‌های HTML/JS در مرورگر برای RTL، عرض ۳۲۰/۳۶۰/۳۹۰/۴۳۰/۵۴۰/۷۶۸ و دسکتاپ، خطای JS، سرریز افقی، نمایش Modal و مقایسه screenshot با baseline ثابت. اسکرین‌شات در سیستم‌عامل و مرورگر ثابت اجرا شود تا false positive کمتر باشد.
3. **Maestro**: سفرهای End-to-End روی APK و Android Emulator یا گوشی آزمایشی، با فایل‌های YAML خوانا؛ ورود، تغییر تقویم، افزودن رکورد آزمایشی، تسویه جزئی، گزارش، backup و کنترل نوارهای اندروید.
4. **Gradle/Robolectric و Android instrumentation**: آزمون مسیرهای Android native (فایل، مجوزها، تقویم، نمایش WebView، import Excel و رفتار فعالیت‌ها)، روی CI و شبیه‌ساز.
5. **GitHub Actions**: اجرای مجموعه آزمون‌های سریع هنگام commit و آزمون‌های کامل‌تر هنگام ساخت release candidate؛ انتشار APK و گزارش آزمون فقط در صورت موفقیت.

## داده آزمایشی استاندارد (غیرواقعی)
- یک شرکت آزمایشی، ۳ واحد سازمانی، ۵ سرفصل، ۳ حساب چهاررقمی، ۲ بودجه متوالی، چند کار و دریافتنی/پرداختنی.
- نمونه‌ها: مبلغ صفر، مبلغ بسیار بزرگ ریالی، کد تکراری، سررسید پیش/پس از دوره، سال کبیسه، تاریخ نامعتبر، تسویه جزئی/کامل، ابطال تسویه، عملیات تکراری.
- برای هر سناریو، پیش از آزمون فایل backup داده آزمایشی ساخته شود و پس از آزمون به snapshot تمیز برگردد.
- هرگز از اطلاعات واقعی یا اطلاعات شناسایی‌کننده افراد برای آزمون خودکار استفاده نشود.

## موارد حیاتی و معیارهای قبولی
| شناسه | سناریو | نتیجه مورد انتظار |
|---|---|---|
| FIN-01 | بودجه سرفصل و واحد ۱ میلیارد ریال، ۴۰۰ میلیون عملکرد، ثبت تسویه ۲۰۰ میلیون | مانده بعد ۴۰۰ میلیون ریال؛ دقیقاً یک گردش |
| FIN-02 | اجرای دوباره همان تسویه با شناسه یکسان | ثبت مضاعف انجام نشود |
| FIN-03 | تسویه ۲ مرحله‌ای در ۲ دوره | هر مرحله در دوره تاریخ واقعی خودش |
| FIN-04 | ابطال تسویه | مانده تعهد و گردش مرتبط به‌طور سازگار اصلاح/معکوس؛ سابقه محفوظ |
| FIN-05 | حساب/سرفصل/واحد دارای گردش | حذف ممنوع؛ پیغام واضح |
| FIN-06 | واردکردن Excel دارای کد/تاریخ/مبلغ نامعتبر | ردیف ناسالم وارد نشود؛ گزارش خطای دقیق |
| FIN-07 | بودجه‌های متداخل یا غیرمتوالی | مطابق سیاست تسلسل، رد با علت روشن |
| DATE-01 | تغییر شمسی/میلادی در تقویم | همان روز واقعی حفظ شود |
| DATE-02 | دکمه «امروز» | روز واقعی گوشی انتخاب شود؛ سال بدون جداکننده |
| DATE-03 | مرز سال و کبیسه | تبدیل، فیلتر و مرتب‌سازی بدون جابه‌جایی روز |
| UI-01 | همه صفحات در عرض‌های موبایل مختلف | هیچ سرریز افقی و دکمه پنهان یا فیلد کوتاه‌شده غیرمجاز |
| UI-02 | بازشدن صفحه‌کلید، status bar، navigation bar، بریدگی نمایشگر | کنترل‌ها قابل مشاهده و دسترسی |
| DATA-01 | backup → حذف نصب روی محیط آزمایشی → restore | تعداد و مجموع رکوردها و checksum داده اصلی یکسان |
| DATA-02 | migration از نسخه قبل روی داده آزمایشی | عدم حذف، دوباره‌شماری یا جابه‌جایی تاریخ |

**مهم:** نمونه‌های فوق طرح آزمون هستند؛ تا زمانی که اسکریپت اجرایی و گزارش آن تولید نشده، نباید آن‌ها را «آزمون پاس‌شده» اعلام کرد.

## تقسیم آزمون برای سرعت
- **هر تغییر کد (سریع):** آزمون‌های Node + lint/کامپایل پایه + کنترل سرریز صفحات اصلی در مرورگر.
- **هر APK آزمایشی:** آزمون‌های Android unit + Maestro چند سناریوی اصلی + شبیه‌ساز Android + خروجی گزارش و screenshot.
- **قبل از ارائه به کاربر:** restore از backup آزمایشی، سناریوی تسویه/ابطال/Excel، مقایسه جمع بودجه و گردش نقدی، آزمون موبایل با حداقل دو اندازه نمایش.
- **بعد از دریافت بازخورد:** ثبت defect و آزمون بازتولید آن؛ افزودن تست regression برای جلوگیری از تکرار همان خطا.

## گزارش آزمون استاندارد
- شناسه آزمون / شماره نسخه و SHA / تاریخ اجرا / نسخه Android و اندازه نمایشگر
- ورودی و مراحل اجرا
- انتظار / نتیجه مشاهده‌شده
- PASS / FAIL / SKIPPED
- متن خطا و تصویر یا ویدئو بدون اطلاعات شخصی
- درجه اهمیت: بحرانی مالی، عملکردی، ظاهری

## کنترل‌های ویژه فاز آینده چندکاربره
- کاربران با نقش‌ها و واحدهای متفاوت، ممنوعیت مشاهده یا تغییر داده واحد دیگر.
- دسترسی فقط سروری کنترل شود.
- دو دستگاه هم‌زمان یک سند را اصلاح کنند: تشخیص conflict و جلوگیری از بازنویسی خاموش.
- تکرار درخواست API یا قطع ارتباط هنگام پرداخت: گردش دوباره ایجاد نشود (idempotency key).
- همگام‌سازی آفلاین با ثبت نسخه سند، حذف منطقی و ترتیب رخدادها؛ نتیجه برگشت به sync آشکار باشد.

## مسیر عملی پیشنهادی
ابتدا یک بسته «داده نمونه + ۱۰ سناریوی مالی + ۵ سناریوی موبایل» بسازیم و به GitHub Actions اضافه کنیم. پس از تثبیت، پوشش آن را مرحله‌ای بالا ببریم. هیچ اجرای خودکار روی دیتای شخصی/عملیاتی انجام نمی‌شود.
